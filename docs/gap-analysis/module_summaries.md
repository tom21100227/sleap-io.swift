### Labels container API surface (Labels.swift, LazyFrameList.swift, LazyDataStore.swift) + LabelsSet
(38 gaps)

The Swift `Labels` is a thin (~384-line) container covering frame storage (eager + lazy/LazyFrameList), basic queries (`frame(for:at:)`, `frames(for:)`, `instances(for:)`), a few structural mutators (`addFrame`, `removeFrame`, `clearPredictions`, `removeTrack`, `merge`), `materialize`, tensor export via a separate `TensorCodec`, and `DictionaryCodec`. Python (4034 lines) and JS (2696 lines) expose a vastly larger surface: rich `__getitem__`/`find` with foreign-video resolution, `numpy`/`from_numpy`/`update_from_numpy`, `clean`/`remove_predictions`/`extract`/`split`/`make_training_splits`/`trim`, full skeleton node management (`rename_nodes`/`remove_nodes`/`reorder_nodes`/`replace_skeleton`), video management (`add_video`/`replace_videos`/`replace_filenames`/`match_video`/`apply_crops`), per-annotation query families (`get_rois`/`get_masks`/`get_bboxes`/`get_centroids`/`get_label_images`), matcher-based `merge`/`match` with `MergeResult`/`MatchResult`/provenance history, cached frame/track indices (`get_frame`/`get_track_annotations`/`reindex`), the `n_user_instances`/`n_pred_instances`/`n_frames_per_video`/`n_instances_per_track` counts, `copy`, and the entire `LabelsSet` container. Most of these are absent in Swift. For a SwiftUI annotation GUI the highest-priority gaps are O(1) frame/track lookup, foreign-video resolution, skeleton/video editing wrappers, `clean`/`remove_predictions`, annotation query families, `copy`, suggestion/track management, and the `numpy`/`from_numpy` round-trip for the training backend. The Swift `merge` is present but a simplified identity-only version that diverges substantially from the canonical matcher-driven pipeline.

### Instance / PredictedInstance / LabeledFrame model + Point/PointsArray + bbox/centroid/identity types
(39 gaps)

The Swift port has the skeleton of the model layer (Instance, PredictedInstance, LabeledFrame, Point, PointsArray, Track) with correct identity semantics and an efficient interleaved-Float32 PointsArray, but it is missing the large majority of the behavioral surface present in Python and JS. Critically absent are numpy()-equivalent accessors on Instance/PredictedInstance/LabeledFrame, n_visible/is_empty/centroid_xy, update_skeleton/replace_skeleton, from_numpy/empty/dict+array constructors, and IoU/pose/identity comparison helpers — all of which the Python and JS ports implement fully. LabeledFrame.merge() is a simplified stub that does not perform spatial matching, return conflicts, merge frame-level annotations, or resolve is_negative; it also lacks remove_empty_instances, remove_predictions, unused_predictions, append, matches, and the centroids/bboxes/masks/rois/label_images annotation containers entirely. Three first-class annotation type hierarchies — Centroid, BoundingBox, and Identity — plus the 3D pose types (Instance3D/PredictedInstance3D) have no Swift equivalent at all. The GUI north star is most blocked by missing numpy/centroid/bbox accessors (rendering overlays, selection hit-testing), the real merge cascade (proofreading workflows), update/replace_skeleton (skeleton editing), and the annotation containers; the backend is most blocked by numpy(invisible_as_nan), per-instance numpy with scores, and from_numpy round-tripping.

### Skeleton / Node / Edge / Symmetry model + skeleton JSON/YAML/SLP codecs + Video model
(34 gaps)

The Swift Skeleton model covers the core mutation surface (addNode/removeNode with instance migration, addEdge, addSymmetry, O(1) name/index lookup, identity equality) and even adds GUI-friendly migrating variants Python/JS lack. But it is missing the entire derived-accessor surface Python exposes for training/inference and matching: node_names, edge_inds, edge_names, symmetry_inds/symmetry_names, get_flipped_node_inds, require_node, rename_node(s), reorder_nodes, match_nodes/matches/node_similarities, name/int indexing, __contains__, and the bulk add_* helpers. The SLP skeleton codec (SkeletonCodec.encodeToNetworkX/decodeFromNetworkX) diverges materially from Python's SkeletonSLPEncoder/SkeletonSLPDecoder: it embeds full py/state node objects instead of integer node indices, uses a string "type":"BODY" instead of the jsonpickle EdgeType py/reduce/py/id scheme, encodes symmetries in a non-standard "graph.symmetries" array rather than type-2 links, and omits the global node-superset dicts — so round-trip fidelity with real .slp files and other SLEAP tools is at risk. There is no standalone skeleton JSON (jsonpickle) codec, no training-config detection, and no YAML codec at all. The Video model is a thin identity stub: it has filename/sourceVideo/backendType/backendMetadata/frameCount/frameSize but lacks shape, grayscale, exists, open/close, is_open, from_filename, replace_filename, original_video, fps, and the whole matches_*/dedup/merge/crop family present in both Python and JS.

### ROI / Mask / LabelImage / Suggestions / Matching-Merge
(18 gaps)

This is the weakest-parity area of the Swift port. The ENTIRE matching/merge subsystem (matching.py / matching.ts, ~1900 LOC) is absent: no SkeletonMatcher/InstanceMatcher/TrackMatcher/VideoMatcher, no match-method enums, no MergeResult/MatchResult/ConflictResolution/MergeError, no FrameStrategy, and the supporting model methods (Skeleton.matches, Skeleton.node_similarities, Instance.same_pose_as/same_identity_as/overlaps_with, Track.matches, Video.matches_path/content/shape) are not implemented. Swift's only merge is a coarse identity-keyed LabeledFrame.merge with a 6-case enum that does NO spatial/IoU instance matching, returns no result/conflict objects, and does no video/skeleton/track correspondence — it is not behaviorally compatible with upstream. ROI, SegmentationMask, and SuggestionFrame exist but as simplified single-struct value types that diverge from upstream's abstract User/Predicted class hierarchy, drop most geometry operations, and (for ROI/mask) carry no WKB or scale/offset support. LabelImage (dense integer per-pixel segmentation, label_image.py / label-image.ts) is entirely absent. Note: there is no upstream symbol literally named "MatchedFrame"; the prompt's reference maps to MatchResult/MergeResult plus LabeledFrame.merge — all missing. Suggestion generation is not a library feature in Python or JS (only the SuggestionFrame data type exists), so no generator gap applies.

### SleapHDF5/SLP (SLP HDF5 read/write, lazy/streaming, embedded video, versioning, provenance, sessions/cameras, ROIs/masks)
(23 gaps)

Swift covers the SLP 1.0-1.5 core well: /frames, /instances, /points, /pred_points compound datasets read+write with field-by-field column reads, lazy column store with LRU cache + on-demand materialization, eager path, embedded-video read (vlen/fixed-length/raw HDF5, PNG/JPEG end detection, channel_order, frame_numbers, source_video JSON), tracks, suggestions (with group), negative_frames, pre-1.1 coordinate adjustment, <1.2 tracking_score gating, from_predicted linking, and basic ROI/mask read+write. However it hard-caps at format 1.5 (`kMaxSupportedFormatVersion`), throwing `formatVersionTooNew` on any file >=1.6 — which current Python writes routinely (1.9 for predicted/instance-linked masks, 2.0 bboxes, 2.1 spatial transforms, 2.3 crops, 2.4 mask provenance). That alone blocks reading most modern projects. Whole annotation families present in Python AND JS are entirely absent in Swift: bounding boxes (/bboxes), centroids (/centroids), label images (/label_images), identities (/identities_json), score maps, and /video_crops. Sessions/cameras are technically present but Swift reads/writes a bespoke `camera_to_video` JSON schema that does NOT match the Python/JS `calibration`+`camcorder_to_video_idx_map`+`frame_group_dicts` format, so multiview round-trips are incompatible and drop all calibration, frame groups, instance groups, and 3D instances. There is no embed-on-save pipeline (embed="all"/"user"/"suggestions"/"source", VideoReferenceMode) — Swift can only copy pre-existing embedded groups or dump an in-memory cache. ROI/mask write also diverges (no predicted variants, no scale/offset/tracking_score/instance/from_predicted columns, no roi_*/mask_* string datasets, no gzip), and provenance is lossily coerced to `[String:String]`.

### Import/Export Codecs: COCO, CSV, Label Studio, AlphaTracker
(21 gaps)

All four Swift codecs exist but diverge substantially from the Python reference in format schema, not just feature coverage. Two are functionally broken against real upstream files: the AlphaTracker reader expects an invented schema (image_path/animal_id/keypoints[[x,y]]/confidence) that no real AlphaTracker file uses — Python's actual format is a list of {filename, class:"image", annotations:[{class:"Face"...},{class:"point",x,y}]} objects, so the Swift reader throws unsupportedFormat on every genuine file. The Label Studio codec uses a parentID grouping convention for both read and write instead of Python's rectanglelabels-individuals + relation (from_id/to_id) structure, making Swift LS files non-interoperable with Python in both directions, plus Swift requires an explicit SkeletonMapping where Python infers nodes automatically. The CSV codec implements a completely different format family (long-table video,frame_idx,skeleton,instance,node,x,y,... one-row-per-point) than Python's pandas-DataFrame-backed formats (sleap/dlc/points/instances/frames with auto-detection, metadata sidecar JSON, chunking, DLC delegation) — there is zero format overlap, so neither can read the other's output. COCO is the closest to parity for the keypoints path but omits detection-only ROIs/masks/bboxes, segmentation (polygon + RLE), binary-vs-ternary visibility encoding option, multi-image-shape video grouping, track export via attributes.object_id, panoptic format, image-filename control, and dataset-root path resolution. None of these codecs are exposed via Python-compatible numeric/array export and several edge cases (NaN handling, score semantics, predicted-point scores defaulting to 0) differ.

### DLC / JABS / Ultralytics-YOLO / Analysis-HDF5 import-export
(23 gaps)

Across these four converters, the Swift port is materially behind both Python and JS, and in two cases reads/writes the wrong on-disk format entirely. The Swift AnalysisHDF5Codec uses dataset name `locations` with a fixed `(T,N,K,2)` canonical layout, but the real SLEAP analysis format (Python + JS) names it `tracks` and defaults to the MATLAB preset `(n_tracks, 2, n_nodes, n_frames)` with `dims`/`preset` attributes — so the Swift codec cannot read genuine SLEAP analysis files nor produce them, and has none of the preset/axis-ordering machinery, occupancy filtering, or `to_analysis_arrays` untracked slotting. The Swift JABSCodec reads a generic 4D `poseest/points` keyed off a `node_names` attribute and writes a single generic layout; it ignores the real JABS pose-version model (v2 single-mouse 3D, v3 `instance_track_id`+`instance_count`, v4+ `instance_embed_id`, the y/x coordinate flip, the built-in 12-node "Mouse" skeleton with edges+symmetries, and v5 static-object ROIs), so it interoperates with neither Python nor JS JABS files. The Swift DLCCodec reads pandas HDFStore "fixed" HDF5, whereas Python (and only Python — JS has no DLC at all) reads DLC annotation CSVs plus full project/config.yaml/train-test-split support; the two do not read the same files. The Swift YOLOCodec is pose-only, single-class, uses the wrong config filename (`dataset.yaml` vs `data.yaml`), and lacks detection/segmentation tasks, bounding boxes, ROIs, splits, and LabelsSet — features present in both Python and JS.

### io/{geojson, trackmate, seq, tiff, nwb, nwb_annotations, nwb_predictions, leap}
(13 gaps)

None of the six focus-area formats (GeoJSON, TrackMate, SEQ, TIFF/LabelImage, NWB, LEAP .mat) exist in the Swift port — there are no corresponding source files under Sources/, and the model prerequisites are also missing or divergent. Two of these formats are also implemented in the JS port (GeoJSON + TrackMate, plus TIFF label-images), so they are clearly in scope for cross-platform parity; SEQ, NWB, and LEAP are Python-only. The Swift ROI model is a flat [SIMD2<Float>] points struct with no Shapely-equivalent geometry (Polygon/MultiPolygon), no __geo_interface__/toGeoJSON, and no from_polygon/from_box/is_bbox/area/centroid — so even the lightweight GeoJSON path needs both a model upgrade and a codec. The Swift port has no Centroid/PredictedCentroid model (blocking TrackMate) and no LabelImage/from_binary_masks model (blocking TIFF). NWB and LEAP depend on the Python/h5py-only ecosystem (pynwb, ndx-pose, ndx-multisubjects, pymatreader) with no Swift equivalents and are correctly flagged out-of-scope in CLAUDE.md Phase 5; they remain low-priority for an Apple-native GUI/backend.

### Codecs: DictionaryCodec + TensorCodec (numpy/tensor export, dataframe export, skeleton YAML, training-config parsing)
(17 gaps)

The Swift port has a functioning round-trip `DictionaryCodec` (encode/decode Labels) and a `TensorCodec.toTensor` that produces a 4D [frames, tracks, nodes, 2/3] array, but both are significantly simpler than the Python and JS references. The dictionary format diverges structurally from Python/JS (uses keys "frames"/"video"/"skeleton" instead of "labeled_frames"/"video_idx"/"skeleton_idx", and serializes full nested skeleton/edge dicts rather than index references), so it is NOT JSON-interchange-compatible with the canonical format. TensorCodec has two correctness bugs vs Python `to_numpy`: (1) the frame axis is indexed by frameStore position rather than `frame_idx - first_frame` so frame alignment to video timeline is wrong, and (2) all untracked instances collapse into track slot 0, overwriting each other (Python slots them positionally via `untracked=True`). Entirely absent: `from_numpy`/`from_tensor` (array -> Labels), the full `to_analysis_arrays` builder API in SleapIO (occupancy/point_scores/instance_scores/tracking_scores tuples — though SleapHDF5.AnalysisHDF5Codec.write reimplements a partial version), the entire dataframe codec (points/instances/frames/multi_index formats + from_dataframe), skeleton YAML, and training-config skeleton parsing. Backend relevance is high for the numpy fixes and from_numpy; GUI relevance centers on dictionary interchange fidelity and is otherwise low for dataframe/analysis paths.

### SleapRendering (PoseRenderer + Colors + RenderOptions) vs Python sleap_io.rendering / sleap-io.js src/rendering
(19 gaps)

The Swift port has a minimal CoreGraphics pose renderer that draws edges, circle nodes, optional node-name labels, track-name text, and a dashed bounding box, colored only by instance index. It is dramatically behind both Python and JS, which share a rich, feature-complete rendering pipeline: a full color system (resolve_color with hex/named/grayscale/palette-index specs, 9-13 palettes, color_by track/instance/node/auto schemes), five marker shapes, motion trails, segmentation/label-image/ROI/bbox/centroid overlays with per-track coloring, pre/post/per-instance callbacks with world_to_canvas, cropping (pixel + normalized), solid-color backgrounds, single-image and full video rendering with ffmpeg/skia, and image/PNG/JPEG export. For a SwiftUI sleap-label replacement the highest-value missing pieces are color_by="track" coloring (consistency across frames is essential for track editing), marker shapes, score/visibility-aware node styling, ROI/mask/centroid overlays (these models exist in Swift but aren't drawn), and a SwiftUI-friendly render-into-context API; trails, callbacks, cropping, and video export are secondary. The backend (sleap.swift) needs almost none of this except possibly headless frame compositing for QC montages.

### Geometric Transforms (sleap_io.transform: core/frame/points/video)
(19 gaps)

The Python reference implements a full composable transform stack: a `Transform` dataclass with a fixed crop→scale→rotate→pad→flip pipeline, a `to_matrix()`/`output_size()`/`apply_to_points()`/`apply_to_frame()` API, standalone frame ops (crop/scale/rotate/flip/pad with PIL interpolation and OOB fill), standalone point ops (crop/uncrop/scale/rotate/pad + OOB masks), CLI parsers (parse_scale/resolve_scale/parse_crop/parse_pad), and a video/labels pipeline (transform_video, transform_embedded_video, transform_labels, compute_transform_summary). The JavaScript port is intentionally minimal — only the crop subset for SLP 2.3 virtual cropping (cropFrame, cropPoints, uncropPoints) — and omits scale/rotate/pad/flip entirely. Our Swift port sits in between: it has a low-level affine matrix toolkit (AffineTransform2D: identity/translation/scale/rotation/compose) and Instance-level convenience methods (translated/scaled/rotated/cropped/transformed) plus an Accelerate-backed PointsArray.apply(transform:), but it has NO unified Transform type, NO flip, NO pad, NO crop-coordinate offsetting helper, NO frame/image transforms, NO output_size/to_matrix pipeline, NO OOB visibility marking, and NO video/labels-level transform pipeline. For the GUI north star the affine + Instance helpers cover live point editing overlays, but a from-scratch Transform pipeline (especially crop offsetting for virtual crop and flip/rotate around image center with correct center-pixel indexing) would be needed for an augmentation/export feature.

### SleapVideo — Video read/write backends (media, HDF5 embedded, image sequence, SEQ, TIFF, streaming, crop, frame cache, grayscale, channel order, seeking)
(20 gaps)

The Swift port covers the three highest-value read paths for a GUI — AVFoundation media video, an HDF5 embedded-frame backend (in SleapHDF5), and an image-sequence directory backend — plus a per-Video NSCache frame cache and exact/adaptive seek tolerance. Those three are reasonably close to behavioral parity for display. Everything beyond that is missing: there is no grayscale autodetection or forced-grayscale collapse, no Norpix .seq backend, no multi-page/rank-3/rank-4 TiffVideo, no CropVideoBackend, no HDF5 channels_first input_format, no HDF5 crop-pushdown, no streaming/range-request HDF5 reader, and no video writer at all (VideoWriter/MJPEGFrameWriter). The Swift VideoBackend protocol also returns CGImage rather than raw pixel arrays, which means there is no numpy()-equivalent frame-tensor path and grayscale/channel semantics are baked into CGImage RGBA, diverging from Python's (H,W,C) ndarray contract. Channel-order (BGR/RGB) handling for embedded frames is present and faithful; FPS is read for media but never for embedded/seq sources. For unblocking a SwiftUI annotation GUI, the most impactful gaps are grayscale handling, the .seq backend, and TIFF stacks (all are real inputs in behavioral neuroscience labs); for a training backend the missing raw-array frame export and crop-pushdown matter most.

### io/main.py (load_file/save_file dispatch + load_*/save_* family) and io/cli.py (sio CLI) vs Swift LabelsIO + SleapioCLI
(28 gaps)

Python's io/main.py is a large dispatch hub: load_file/save_file auto-detect 13+ formats (slp, nwb, leap/.mat, json -> alphatracker/coco/labelstudio by content-sniff, .h5 -> analysis_h5/jabs by content, geojson, dlc/dlc_project, csv -> trackmate/dlc/csv by content, ultralytics dir, video by extension), with parallel load_slp/save_slp keyword-rich entry points, a remote URL/Google-Drive layer, and helpers (load_skeleton, save_skeleton, load_labels_set, load_label_images, load_video). The JS port (main.ts) covers a much smaller surface: loadSlp/saveSlp (with browser-Worker streaming), loadAnalysisH5/saveAnalysisH5, loadSlpSet/saveSlpSet, loadVideo, isAnalysisH5File, and TIFF label-image readers; it has NO load_file/save_file unified dispatcher. The Swift port's Labels.load/save (LabelsIO.swift) + inferLoadFormat/inferSaveFormat dispatch over a FileFormat enum of 9 formats (slp, cocoJSON, csv, labelStudio, yolo, alphaTracker, analysisHDF5, jabs, deepLabCut) and content-sniff JSON/HDF5; its CLI (SleapioCLI: info/show/convert) is a thin subset of Python's 18-command sio. Major Swift gaps vs Python: no NWB/LEAP/TrackMate/Ultralytics/GeoJSON formats; no .mat/.nwb/.geojson/video/.yaml dispatch; no load_video/load_skeleton/load_labels_set/load_label_images; no remote URL loading; and the CLI is missing 15 of 18 commands (export, split/unsplit, merge, filenames, render, fix, embed/unembed, trim, reencode, apply-crops, transform). Most missing formats (NWB/LEAP) are out of scope on Apple, but the missing CLI commands and load_video dispatch are GUI-relevant.

### CROSS-CUTTING (completeness critic)

The per-module audit was thorough on feature surfaces but systematically skipped cross-cutting infrastructure that spans modules. The biggest blind spots: (1) the canonical public API export contract — Python's __init__.py exposes ~120 flat top-level symbols (load_*/save_*, every model class, every matcher) that downstream code imports as `sleap_io.X`, and JS mirrors most via barrel exports; the Swift port has no umbrella/re-export module or documented public surface, so consumers must reach into nested namespaces. (2) Provenance is typed `dict[str, Any]` upstream (values can be ints/floats/lists/nested dicts, e.g. `provenance["cellpose_diameter"] = 30`) but `[String: String]` in Swift — a silent data-loss/round-trip-corruption bug, not just a feature gap. (3) The multi-camera calibration math (rodrigues_transformation, extrinsic_matrix composition, CameraGroup, the rvec/tvec attrs validation, FrameGroup/InstanceGroup 3D point aggregation) is barely covered — the audit only noted session serialization schema mismatch. (4) Remote/URL/Google-Drive loading (io/_remote.py ~1029 LOC, io/_gdrive.py ~521 LOC) with magic-byte sniffing, HTTP range requests, retry/backoff, and RemoteIOError is entirely absent and was only mentioned in passing. (5) io/utils.py HDF5 helpers, version.py/__version__, format version-migration write path (Swift can read 1.0-1.5 but always writes one fixed version with no migration/downgrade), and async/Sendable/actor-isolation contracts for a SwiftUI @MainActor GUI were not audited as cross-cutting concerns. GUI-critical additions: a public observable/diffable model layer (Swift classes are @unchecked Sendable mutable refs with no Combine/Observation conformance, no change notification, no undo/redo), and stable identity/equality/hashing for SwiftUI ForEach/Identifiable.
